# ПО серверов: инвентаризация, план и обновление

Ansible-проект запускается **с ноутбука или управляющего Linux-сервера** и подключается
по SSH к списку IP/DNS. Четыре действия выбираются через меню или аргумент командной строки:
инвентаризация, план, обновление и проверка SSH-доступа.
По умолчанию никакие обновления не устанавливаются. Перед первым запуском заполните
список адресов и проверьте SSH/sudo.

## Быстрый запуск

На машине запуска нужны Python **3.12+**, OpenSSH и доступ к серверам. Подходит macOS/Linux.
Для инвентаризации на целевых серверах нужны SSH, Python **3.7+**, `dpkg-query` и APT,
для обновления — root/sudo. Проверке SSH нужен только доступ по ключу и обычная shell.
Инвентаризация и установка используют `ansible.builtin.script`, поэтому не требуют
`python3-apt` или установки нового Python на старые версии Astra.
**Автоматическая перезагрузка** использует стандартный модуль Ansible и требует
Python **3.9+** на сервере; это проверяется до установки пакетов.

```bash
git clone https://github.com/shilvlad/server-os-upgrade.git
cd server-os-upgrade/fleet
python3.14 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp servers.example.txt servers.txt
```

В `servers.txt` оставьте IP или DNS-имена, по одному серверу на строку. Можно смешивать
IPv4, IPv6, полные DNS-имена и короткие имена (разрешаются средствами SSH/системы).
Пустые строки и комментарии `#` пропускаются; повторы удаляются, регистр DNS не учитывается.
Международные домены преобразуются в IDNA. Например:

```text
192.0.2.10
2001:db8::10
app01.example.com
db01
```

Это примеры, их нужно заменить. URL, `user@host`, `host:port` не принимаются —
пользователь задаётся через `--user`, порт через inventory или SSH config.
Имя `localhost` зарезервировано управляющим узлом Ansible; для SSH к нему укажите IP.
Если `--hosts`/`-i` не заданы, автоматически используется `servers.txt` рядом с `run.py`,
если он существует; иначе — `inventory/hosts.yml`.

При первом SSH-подключении проверьте fingerprint ключа сервера по доверенному каналу
и сохраните его в `known_hosts`. Проверка ключей в проекте включена.
Пароли запрашиваются Ansible и не записываются в файлы проекта.

```bash
# Меню выбора; -K нужен, если sudo требует пароль.
python run.py --hosts servers.txt --user ops -K

# Инвентаризация без изменения пакетов или сервисов.
python run.py inventory --hosts servers.txt --user ops -K

# План по текущим APT-индексам, без установки и обновления индексов.
python run.py plan --hosts servers.txt --user ops -K

# Получить свежие индексы и затем рассчитать план. Меняются только APT-индексы.
python run.py plan --hosts servers.txt --user ops -K --refresh-cache

# Установка: свежие индексы + apt-get upgrade, серверы строго по одному.
# Без --yes потребуется ввести UPDATE. --limit позволяет начать с одного узла.
python run.py update --hosts servers.txt --user ops -K --limit 192.0.2.10

# Явно разрешить пакетное обновление Astra; сертификат/выпуск не мигрируется сценарием.
python run.py update --hosts servers.txt --user ops -K --astra-apt

# dist-upgrade с разрешением новых зависимостей; удаление пакетов по-прежнему запрещено.
python run.py update --hosts servers.txt --user ops -K --astra-apt --full-upgrade

# По желанию перезагрузить каждый успешно обновлённый узел и проверить его повторно.
python run.py update --hosts servers.txt --user ops -K --astra-apt --reboot

# Неинтерактивное подтверждение, например из своего терминала с NOPASSWD sudo.
python run.py update --hosts servers.txt --user ops --astra-apt --yes

# Проверить сценарий обновления без установки, обновления индексов и перезагрузки.
python run.py update --hosts servers.txt --user ops -K --check
```

`--ask-pass` включает SSH-пароль, `--private-key /путь/к/ключу` выбирает ключ.
Если не указать `--user`, SSH использует свои настройки/текущего пользователя.
Инвентаризация создаёт временные файлы Ansible на сервере и локальные отчёты;
пакеты и сервисы она не изменяет. Настраиваемые version-команды должны быть без побочных действий.

## Проверка SSH перед инвентаризацией

В меню выберите **4 — Проверка подключения по SSH-ключу**. Режим проверяет все выбранные
серверы из `servers.txt`, продолжая обход при ошибках отдельных узлов.
Отдельный запуск без меню:

```bash
ssh-add ~/.ssh/id_ed25519
python run.py check-ssh --hosts servers.txt --user ops --private-key ~/.ssh/id_ed25519
```

Замените `ops` и путь ключа своими значениями. Для меню с тем же ключом:

```bash
python run.py --hosts servers.txt --user ops --private-key ~/.ssh/id_ed25519
```

Проверяется **новое SSH-соединение с аутентификацией по ключу и выполнение `/bin/true`**.
Парольный вход и использование ранее открытого ControlMaster-соединения исключены.
`--ask-pass` несовместим с этим режимом; переданный меню `-K` здесь игнорируется,
sudo и Python на сервере не используются. Зашифрованный ключ заранее загрузите в SSH-agent.
Проверка ключа сервера в `known_hosts` остаётся включённой.

Для каждого узла выводятся OK или ошибка: DNS, отклонённый/недоступный ключ,
`known_hosts`, отказ SSH-порта, сеть или тайм-аут. Стандартный тайм-аут подключения —
10 секунд; можно изменить через `--ssh-timeout 20`. Параметры `--limit`, `-i`,
SSH config и `ansible_ssh_common_args` для ProxyJump поддерживаются.
При ошибке хотя бы одного узла код завершения ненулевой.

Результат сохраняется в `reports/<запуск>/summary.md` и `ssh-check.json`.
Этот режим создаёт только отчёт о подключении; состав ПО собирается отдельным пунктом меню.

## Что инвентаризируется

| Источник | Что сохраняется | Ограничение |
|---|---|---|
| ОС и ядро | Дистрибутив, выпуск, кодовое имя, `/etc/astra_version`, архитектура, работающее ядро | Не проверяет сертификационный статус конфигурации |
| DPKG | Все пакеты в состоянии `installed`, в том числе held; полные binary/source версии и архитектура | Не включает ПО, установленное вне DPKG |
| Python | Метаданные системных пакетов и найденных/заданных venv | Каталоги окружений вне областей поиска нужно указать |
| npm | Глобальные пакеты текущего пользователя | Зависимости отдельных Node.js-приложений не обходятся |
| Snap / Flatpak | Имена и версии, доступные пользователю запуска | Установки других пользователей могут быть не видны |
| Docker / Podman | Локальные контейнеры и образы, ID/digests | **Пакеты внутри образов не сканируются**; нужен отдельный SBOM/скан образа |
| `/opt`, `/usr/local`, `/srv` | Каталоги и исполняемые файлы, ограниченный поиск до 3 уровней / 500 записей | Это кандидаты на ручную проверку, а не доказанный список всего ПО |
| Version-команды | Java, OpenSSL, Python, Node.js, Go, Docker, Podman и ваши проверки | Для неизвестного бинарного ПО нужно задать команду версии |

Переменные и пароли контейнеров, содержимое конфигураций и командные строки процессов
не собираются. Docker запрашивается через локальный `/var/run/docker.sock`, Podman —
в локальном режиме. Для rootless-контейнеров, пользовательского Flatpak/npm и других
домашних установок нужен отдельный запуск от соответствующего пользователя
с `ansible_become: false` в его inventory/переменных. Недоступный сборщик помечается
как `not_available/error/partial`; это не означает отсутствие ПО.

Для произвольных бинарных файлов, JAR, зависимостей проектов и всех контейнерных слоёв
универсальную полноту такой сборщик гарантировать не может. Известные дополнительные
источники задаются в конфигурации, а обнаруженные кандидаты проверяются отдельно.

## Настройка серверов и дополнительных проверок

Для разных логинов, SSH-портов и других параметров подключения используйте inventory:

```bash
cp inventory/hosts.example.yml inventory/hosts.yml
cp local-vars.example.yml local-vars.yml
# Измените файлы под свои серверы.
python run.py inventory -i inventory/hosts.yml --vars local-vars.yml -K
```

`local-vars.yml` задаёт общие параметры. Для разных серверов можно создать
`inventory/host_vars/astra01.yml` или группы в `inventory/group_vars/`.
Эти рабочие каталоги исключены из Git. Переменные `fleet_venv_paths`,
`fleet_discovery_roots`, `fleet_custom_probes`, `fleet_critical_services`
показаны в `local-vars.example.yml`. В `argv` передавайте список аргументов:
shell, конвейеры и подстановка команд не выполняются.

Перед обновлением укажите действительно критичные сервисы для каждого узла:
проверяется их `systemctl is-active` до установки и после неё/перезагрузки,
а также появление новых systemd units в состоянии failed. Пустой список
не обеспечивает проверку работоспособности приложений, HTTP API или кластера.
Переключение лидеров, drain Kubernetes, балансировщик и резервное копирование
в этот сценарий не входят. Для HA-систем вначале выбирайте конкретный узел через `--limit`.

## Как работает обновление

### Подключение отсутствующего security-репозитория Ubuntu

Если `apt-cache policy` не содержит `jammy-security`/`noble-security`, можно использовать
отдельный плейбук для **Ubuntu 22.04/24.04 amd64**. На целевых серверах нужен
системный Python 3.9+ и `python3-apt`. Действующий SSH config используется как обычно.

Сначала просмотрите изменение:

```bash
ansible-playbook -i inventory/generated.json playbooks/ubuntu-security.yml --check --diff
```

Применение источника и обновление индексов:

```bash
ansible-playbook -i inventory/generated.json playbooks/ubuntu-security.yml
python run.py plan --hosts servers.txt --refresh-cache --full-upgrade
```

Плейбук определяет выпуск Ubuntu, проверяет штатный ключ архива и при отсутствии
security-индекса создаёт `/etc/apt/sources.list.d/fleet-ubuntu-security.sources`.
Источник — `https://security.ubuntu.com/ubuntu/`, подпись проверяется через
`ubuntu-archive-keyring.gpg`. После обновления индексов проверяется появление нужного
security pocket. При ошибке обновления/проверки новое изменение файла откатывается.
Повторный запуск при уже доступном security-индексе не создаёт дополнительный источник.
Пакеты приложений и ОС устанавливаются отдельным действием `update`.

### Установка пакетов

1. Проверяет ОС, `dpkg --audit`, критичные сервисы, свободное место на `/`, `/var`, `/boot`.
   По умолчанию минимум 2048 MiB для `/` и `/var`, 200 MiB для `/boot`; эти пороги
   настраиваются через `fleet_min_root_free_mb`, `fleet_min_boot_free_mb` и не заменяют
   расчёт места для конкретной транзакции.
2. Сохраняет снимок ПО `before`, обновляет APT-индексы и сохраняет симуляцию APT.
3. Повторяет симуляцию непосредственно перед установкой и выполняет `apt-get upgrade`
   либо выбранный `dist-upgrade` с `--no-remove`. Существующие held-пакеты сохраняются.
   `autoremove`, downgrade и отключение проверки подписей не используются.
4. Проверяет DPKG и сервисы, по отдельному флагу перезагружает сервер,
   сохраняет проверки и снимок ПО `after`. При ошибке следующие серверы не обновляются.

Используются **только уже настроенные репозитории и APT pinning**. Сценарий не меняет
`sources.list` и не является инструментом миграции дистрибутива. Перед запуском
проверьте, что репозитории относятся к нужному выпуску: плавающий alias вроде
Debian `stable` может уже указывать на другой выпуск. План — снимок состояния,
а не фиксация версий: между просмотром и установкой репозитории/состояние пакетов могут измениться.

Для **Astra Linux** установка блокируется до явного `--astra-apt`. Это разрешение
обновить пакеты из ваших репозиториев через APT, **не замена штатной процедуры
обновления выпуска через `astra-update`**. Для сертифицированных систем используйте
разрешённые репозитории и регламент для конкретной версии Astra. Миграцию выпуска
следует выполнять отдельным сценарием, адаптированным к инструкции производителя.

APT/maintainer scripts могут перезапускать сервисы. Без `--reboot` сервер не перезагружается,
но отсутствие `/var/run/reboot-required` не доказывает, что перезагрузка не нужна.
Обновление Snap, Flatpak, pip/npm и образов контейнеров этим действием не выполняется.
Автоматического отката/снимка VM нет. Транзакция APT не прерывается собственным тайм-аутом;
блокировки DPKG не удаляются. Логи не заменяют резервную копию.

## Отчёты и проверка уязвимостей в чате

Каждый запуск создаёт отдельный каталог `reports/<UTC-время>-<идентификатор>/`.

| Файл | Назначение |
|---|---|
| `summary.md` | Серверы, число DEB-пакетов, пробелы в сборе и ошибки |
| `inventory.json` | Полный собранный состав ПО с адресами серверов |
| `packages.csv` | Плоская таблица DEB-пакетов для Excel/фильтрации |
| `review.json` | Данные для проверки в чате: хосты заменены на `host-0001` и т. д.; нет IP, имён контейнеров и путей окружений |
| `run.json`, `run-status.json` | Действие, выбранные серверы, код завершения и фактический результат Ansible |
| `hosts/*.json` | Снимки `before/after`, планы, результаты установки и проверки сервисов |
| `ssh-check.json`, `ssh-results.json` | Результаты режима `check-ssh` и исходные сообщения SSH |

При ошибке берётся последний доступный снимок; его фаза указывается в `review.json`.
Недоступные и ещё не обработанные после остановки серверы учитываются отдельно.
Права каталога отчёта — 0700, файлов — 0600. Отчёты, IP/DNS и рабочие настройки
исключены из Git. Альтернативные пути для `--reports`/inventory вне исключений
нужно защищать самостоятельно. Файлы не отправляются в GitHub или чат автоматически.

Для проверки приложите **`review.json`** и напишите:

> Проверь состав ПО по актуальным официальным бюллетеням Astra/Debian/Ubuntu,
> производителей ПО и БДУ ФСТЭК. Учитывай полные версии пакетов, выпуск ОС,
> source versions и бэкпорты. Раздели подтверждённые уязвимости, возможные совпадения
> и недостаток данных. Для подтверждённых приведи CVE/BDU, риск, исправленные версии,
> первоисточник и конкретные действия. Не объявляй сервер безопасным при неполном сборе.

Перед передачей просмотрите `review.json`: названия собственных пакетов и вывод ваших
version-команд могут содержать внутренние сведения. Сам проект не обращается к LLM/API,
не требует OpenAI-токена и не выдаёт заключения о наличии/отсутствии уязвимостей.
Для больших парков удобнее прикладывать данные отдельными группами через `--limit`.
